# 369 이미 사용한 DEV 12조건의 검증 분리 계약 확인

**계약 확인만 완료했다. DEV 실제 실행·새 split 개봉·예산 배정·예약·승격은 없다.** 365 후보는 `65df88a5b2391675e49c3f39259adab0f8a791da5ab58ea620cbe130b0a9ce34`로 동결돼 있다. 연구 잔여 **16,842회**, 최종 예비 **84,000회**를 보존했다.

S2960–3의 과거 그룹명 `sealed295`는 당시 아직 성능을 보지 않았던 **DEV 네 조건**을 뜻한다. 공식 SEALED와 다른 역할이다. 나머지 여덟 조건은 296의 DEV reliability 등록이다. 이 12조건은 당시 240 대 g1p4 선택에 이미 쓰였고, 이후 champion 296를 선택한 증거다. 따라서 365가 다시 평가하더라도 새로운 독립 검증 집합이 아니다.

현재 저장된 1,042개 job 신원 메타데이터를 조사했다. 이 296 DEV에 대응하는 job은 296의 두 arm 24개이며, 다른 단계의 추가 실행은 발견되지 않았다. 여기서 말하는 재사용은 이미 champion 선택에 사용한 조건을 다시 평가한다는 뜻이며, 확인되지 않은 여러 후속 실험을 가정하지 않는다.

**297의 미개봉 12조건은 별개다.** 296 대상과 내부 ID·seed·도로 기하가 모두 겹치지 않는다. 297의 performance opening 표식·DEV 결과 폴더·309 개봉 표식이 없고, 현재 job 신원 목록에도 대응 실행이 없다. 298·299 등의 transfer 명세와 원래 297 seal을 기존 DEV 결과로 혼동하지 않았다. 이번에는 그 12조건의 신원·seal 메타데이터만 대조했고 성능을 열거나 selector를 호출하지 않았다.

기존 HOLDOUT 열림 표식은 이미 존재하므로 이를 미사용 HOLDOUT으로 되돌려 부르지 않는다. 해당 표식과 protected query ledger는 변경하지 않았다. 현재 champion manifest의 SEALED 상태는 `PENDING_CLOSED`이고 `SEALED*.opened` 표식은 없다. 296 DEV, 297의 미개봉 DEV, 과거 HOLDOUT, 공식 SEALED를 서로 다른 집합·역할로 유지한다.

12개의 원래 job·공식 결과·terminal receipt·전체 action/memory trace·baseline ZIP·추출 멤버·실제로 로드된 모듈 hash를 확인했다. baseline 296 archive는 `0a6c5e286e87d75498c5aec1174c7af3fd54f6efa34b0d83ca1efba5d404a937`다. 양 arm의 초기 영상·기하 hash가 일치하고 현재 365 TRAIN 실행과 Python 3.11.16·numpy 1.26.0·OpenCV 4.8.1 버전이 같다. 296 커밋 이후 env_wrapper·damage·core·local_runner의 tracked 코드 변경도 없다.

따라서 **기존 신원과 역사적 비교 계약을 준비할 자료는 사용 가능**하다. 다만 이번에는 reset을 하지 않았다. 향후 실행 전 기록된 초기 영상·기하와 등록된 물리 장애물 hash를 새 reset에서 확인해야 한다. 과거 296에는 전체 저장 픽셀·매 행동의 GT 물리·평가기 RNG가 없으므로 일치하는 잠재 상태 prefix나 새 동시 paired 대조군이라고 주장할 수 없다. binary 의존성 전체 hash와 공식 서버 동등성도 별도로 증명된 것은 아니다.

제안하는 최대 비용은 **새 후보 12회 × 조건당 2,000 = 24,000행동**이다. 새 baseline은 실행하지 않고 검증한 역사적 296만 비교한다. 최대 act·commit 각각 24,000회, 환경/actor reset 12회, 최대 step raw tick 96,000 + 예상 reset tick 612이다. 최종 예비를 쓰지 않고 전체 최악 상한을 확보하려면 현재 연구 16,842회보다 **7,158회가 추가로 필요**하다. 과거 296의 2,991회 실제 소비는 새 정책 비용의 보장이 아니다. **추가 배정은 제안일 뿐 이번에 집행하지 않았다.**

기존 잔액만 쓰는 별도 선택지도 가능하다. 총 16,842회, 조건당 `min(2,000, 전체 잔여)`로 고정 순서 S2960→S29611을 진행하고 소진 시 멈추는 방식이다. 최악에는 여덟 조건에 각 2,000회, 아홉 번째에 842회 후 세 조건이 미측정으로 남을 수 있다. 이 방식은 12조건 완료를 보장하지 않으며 부분 표·protocol censor로 후보 우세 판정을 하지 않는다. 이번에는 이 대안도 예약하거나 실행하지 않았다.

향후 별도 실행 지시가 있을 때의 사전 판정 기준은 다음으로 제안한다.

1. 동결 365 한 후보와 정확히 같은 12신원·순서를 고정한다. 재추출·조건 대체·다른 후보·threshold 수정은 없다. 초기 신원·버전·입력 전용 및 유효 제어 검증이 실패하면 멈추고 자동으로 baseline을 다시 실행하지 않는다.
2. 자신의 관측·전체 반환 제어·정상 기억으로 공식 완주·은퇴까지 진행하며, 먼저 닿은 2,000 상한·전체 예산·현재 승인 종료 시각에서는 멈춘다. 내부 2,038 상한이나 기간을 자동 연장하지 않는다. 공식 종료 없이 상한에 닿으면 protocol censor로 구분한다.
3. 각 조건 종료 후 다음 reset 전에 알려진 fixture 지원 직접·출생 지원 retained 점의 실제 routing 누락이 각각 0인지 확인한다. 위반이나 기술 오류면 후속 실행을 멈춘다. 확인된 잘못된 fixture 간 low 양성 이력 전파도 자격 반례로 남긴다. GT는 사후 원형 대응에만 쓰고 runtime 특징에 넣지 않는다. 단순 DNF는 기록하고 다음 조건을 진행한다.
4. **12조건의 확정된 비검열 공식 결과가 모두 있어야** 서술적 후보 비교를 한다. baseline은 10완주다. 365가 11·12완주면 완료 수 개선, 0–9면 열세다. 10으로 같으면 공통 완주 조건의 새−과거 공식 lap 평균이 엄격히 음수일 때만 시간상 우세다. 동률·시간 비교 불가면 296를 유지한다. 모든 완주 추가·상실 조건도 공개한다. 전체 완주 증가가 있는 경우 개별 한 조건의 완주 상실만으로 총점 비교를 자동 거부하지 않되 지원점 게이트는 별개의 필수 전제다.
5. DNF에는 임의의 가짜 lap을 부여하지 않는다. 공통 완주 lap의 평균·중앙값·합계·개별 차이와 DNF 진행도·종료 원인을 분리한다. DAMAGE는 진단이며 별도 damage 점수나 median damage veto를 만들지 않는다. 부분 실행·검열·기술 오류는 비교 불충분이다. 어느 결과도 자동 champion 승격·새 G4 인증·다음 split 개봉으로 이어지지 않는다.

현재 README의 공식 기준은 **주행별로 완주가 미완주보다 앞서고, 완주끼리는 실제 시뮬레이션 lap이 짧을수록 우수**하다는 것이다([README](../README.md#8-종료와-점수)). TRAIN에서 365는 18/18, 296는 17/18로 T2950의 완주 하나를 얻었다. 이는 완료 우선 목표에 관련 있는 관측이다. 동시에 공통 17조건은 평균 **0.660초**, 중앙값 1.140초, 합계 11.220초 느리고 15조건이 느리며 2조건이 빠르다. 속도가 좋아졌다는 결과는 아니다.

고정 연구 계약의 완주 수 우선 비교에서는 이 TRAIN 완료 증가가 우선하지만, README는 여러 seed의 한 완주와 몇 초를 교환하는 보편적 집계식을 규정하지 않는다. 임의의 공식 총점 개선량이나 모집단 우세를 만들지 않는다. 공통 완주 시간은 양쪽이 완료한 조건에 한정된 조건부 통계이며 자기 완주 평균·damage·반복 TRAIN 결과로 공식 목적을 대체하지 않는다.

기존 DEV는 이미 선택에 사용됐으므로 미래의 동결 재평가도 독립적인 일반화 증거가 아니다. 현재 365의 모호한 이력 전이 62개와 출생 GT 누락 직접 12개·retained 16개 문맥도 그대로 미해결이다. 새로운 DEV 결과가 좋아도 해당 불확실성이 자동 해소되거나 SEALED 검증을 대체하지 않는다.

이번 읽기 전용 감사는 **native·actor·환경 reset·학습 모두 0**이다. 296의 12개 결과와 2,991개 과거 행동 기록만 검사했다. 성공 감사 벽시계 2.485초·CPU 1.248초이며 코드 작성·git·최초 전송 장애 시간은 포함하지 않는다. 첫 감사 명령은 프로세스 생성 전에 전송 연결 오류로 거부됐고 코드·plan·비용·예산 파일이 없음을 확인한 뒤 읽기 접근이 복구됐다. 실제 감사는 한 번 실행됐으며 새 정책 실행이나 환경 재시작은 없다. 연구 **16,842회**·예비 **84,000회**를 그대로 v385에 기록했다.

champion 296·365·357·main·공식 Participants·기존 사용자 변경과 백업을 보존했다. 공개 저장소에는 일반 감사 코드와 집계 결과만 기록하며 exact identity/seed 명세·GT·모델·개인 문서는 비공개로 유지한다.
